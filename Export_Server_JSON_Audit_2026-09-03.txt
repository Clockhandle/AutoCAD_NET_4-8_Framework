EXPORT (JSON) vs SEND TO SERVER — DATASET AUDIT
Date: 2026-09-03
Scope: Services/ExportService.cs, Services/GeometryProcessingService.cs,
       UI/ExportDialogs.cs, MiningManagerDForm.cs, UI_Events.cs
Requested by: check both output paths, across all categories, for dataset
mismatches. Borehole date-assignment on send-to-server was to be left alone.

=================================================================
1. ARCHITECTURE FINDING (GOOD NEWS)
=================================================================
ExportToFile() and SendToServer() (Services/ExportService.cs:82 and :325)
both call the SAME GenerateCombinedJsonPayload() (:31) for every category:

  Vỉa, Đứt gãy, Nham thạch, Lỗ khoan, Bề mặt,
  Địa hình lò, Địa hình lò Loại 2, Giới hạn

There is no separate/duplicate JSON-building code for the server path.
For a given selection, the two outputs are structurally guaranteed to
match — this rules out most kinds of "dataset drift" between the two
export modes.

=================================================================
2. THE ONE PLACE THEY ACTUALLY DIVERGE — NOT BOREHOLES
=================================================================
The only parameter that differs between the two calls is `date`, and it
is wired ONLY for "Địa hình lò" (Mine Topology loại 1):

  - ExportDialogs.cs:64   -> date picker (dtpDate) only shown when
                             category == "Địa hình lò"
  - ExportService.cs:230  -> ExportToFile() never passes `date` at all,
                             so JSON-file exports of Địa hình lò always
                             get "Date": null
  - ExportService.cs:342  -> SendToServer() passes through whatever date
                             the user picked in the dialog

Checked BoreholeData / DepthInterval / SurveyReading
(Models/MiningDataModels.cs:72-98) and the borehole send dialog:
THERE IS NO DATE FIELD ANYWHERE FOR BOREHOLES, in the dialog or the
model. The "boreholes get a date on send-to-server" caveat as described
does not match what's currently in the tree — it's the Địa hình lò
category that has this behavior. Mine-topology date logic was left
untouched. Flagging in case the borehole date behavior was expected
from a different branch or is planned but not yet wired in.

=================================================================
3. REAL BUGS FOUND
=================================================================
[BUG 1] CountTotalLines() and the diagnostic switch in ExportToFile()
        are missing a case for "Địa hình lò Loại 2"
        (ExportService.cs:567-632 and :95-228).
        Effect: Exporting Loại 2 to JSON works fine, but the success
        dialog always reports "Tổng số lines: 0" for it, and a
        genuinely-empty Loại 2 selection won't get the helpful
        diagnostic message the other categories get.

[BUG 2] SendToServer() has no "empty data" pre-check, unlike
        ExportToFile() (:236-258).
        Effect: If geometry didn't resolve, ExportToFile() catches it
        locally and reports exactly which items failed to resolve.
        SendToServer() will silently POST an empty/near-empty JSON
        array with no local warning — you'd only find out from however
        the server responds (or not at all, if the server accepts
        empty arrays).
        This is likely why "export to JSON usually works" in practice:
        it's not that the datasets differ, it's that only the file path
        checks for broken selections before anything leaves the
        machine.

[NOTE]  Schema isn't fully uniform across categories (same in both
        output paths, so NOT a JSON-vs-server issue, but worth knowing):
        - CreateGioiHanItem (:765) omits "IsHole", which every other
          category's item includes.
        - Bề mặt items key the name as "ViaName" instead of "Name"
          (:500-516).
        If a server-side consumer expects one uniform shape across all
        types, this could read as a "mismatch," but it is consistent
        between file export and server send today.
